## What is the difference between a coding bootcamp and live classes?

Mostly time and intensity. A bootcamp compresses learning into a short, full-time block with a cohort. Part-time live classes spread similar material over a longer period, a few hours a week, alongside the rest of your life.

### A bootcamp, typically

A fixed start date, a cohort that moves together, many hours a week for a few months, and a final project. Many add career coaching. Some are live, some recorded, some mixed; some teach in Spanish, some in English.

Its strength is focus: for people who can stop working for a few months, total immersion is a fast way to build momentum. Its risk is the same compression: there is little time to absorb ideas, and anyone who falls behind in week three may struggle to catch up.

### Our part-time live classes

Twice a week you join a level-matched group of up to twenty, or you book private lessons at times you pick. Each lesson runs in English, led by an India-based mentor who reads what you wrote and asks you to justify it.

The strength is sustainability: you keep your job or degree and still progress every week. The cost is time. Reaching a solid working level usually takes many months, not a few weeks, and we say so before you start.

### What the table says

Programming is the rarest computing skill INEI measures, well below installing software (47.7%) or using spreadsheet formulas (73.7%). The same bulletin finds 15.5% of men and 8.3% of women had written a program in 2026.

### What it means for choosing a course

Our reading: most adults starting a bootcamp or a course in Peru begin from zero in programming, even if they use computers every day. A course that assumes prior coding will lose them; a good one starts with the basics and checks them.

## What skills do software developer jobs actually ask for?

Employers' own frameworks are a better guide than any course brochure. The most detailed public one is O*NET, run for the US Department of Labor, whose profile of software developers lists tasks, skills and knowledge gathered from workers and job postings.

### What O*NET lists for software developers

Under transferable skills, "Programming" comes first, followed by judgement, systems analysis and complex problem solving. The essential skills include critical thinking, reading comprehension, writing and speaking. Under knowledge, alongside computers and mathematics, it lists "English Language".

Among detailed work activities it lists "Develop testing routines or procedures." In the work context, 71% of respondents rated working with or contributing to a team as extremely important. Git appears under its file versioning software.

### The honest part about degrees

O*NET places software developers in Job Zone Four, where "most of these occupations require a four-year bachelor's degree, but some do not". In its education data, 85% of respondents said a bachelor's degree is required. That is US data, and hiring varies by country and company, but it is the official picture.

So we do not tell anyone that a short course replaces a degree. For people who already have one, or are studying for one, a course adds practical skills; for those without, it can be a start, and the evidence that counts is work you can show and explain.

1. **Programming fluency.** Write and read code without notes in at least one language.
2. **Testing.** Check your own code with tests before anyone else sees it.
3. **Version control.** Branches, commits and pull requests in Git.
4. **Data.** Store, query and change data with SQL.
5. **Communication in English.** Read documentation, write a clear message, explain a decision aloud.
6. **Teamwork.** Review others' code and accept review of yours.

That last point is where English matters in Peru. In EF's English Proficiency Index 2025, Peruvians who work in IT score 522, in its "moderate" band. A part-time class in English builds the language and the code together, week after week, which a short full-time sprint has less room to do.

## What does a code review teach that a tutorial does not? A diff lesson in Python

In a job, almost every change you make is read by someone else as a diff: the lines removed and the lines added. Learning to read and write diffs is one of the habits a part-time course has time to build. This lesson uses Python's own difflib module.

### The bug a reviewer would catch

Version 1 of average works for normal input: the marks 14, 17 and 11 give 14.0. But give it an empty list, which happens the first time a class has no marks yet, and it divides by zero.

The program below runs both cases and prints exactly what Python raises: ZeroDivisionError division by zero. A tutorial usually shows the happy path; a reviewer asks "what if the list is empty?"

### How to read the diff

Lines starting with - were removed; lines starting with + were added; lines starting with a space are unchanged context. The header @@ -1,5 +1,4 @@ means five lines from line 1 of the old file became four lines from line 1 of the new one.

The new version guards the empty list first and uses sum() instead of a hand-written loop. SequenceMatcher reports a similarity of 0.22: most of the function changed, which a reviewer should notice and ask about.

**Version 1, and the case it misses** (Python)
```python
def average(marks):
    total = 0
    for m in marks:
        total += m
    return total / len(marks)

print(average([14, 17, 11]))
try:
    average([])
except ZeroDivisionError as e:
    print(type(e).__name__, e)
```

**What Version 1 prints** (Output)
```output
14.0
ZeroDivisionError division by zero
```
Pasted unchanged from a Python 3.14 run.

**The review as a unified diff** (Python)
```python
import difflib

before = '''def average(marks):
    total = 0
    for m in marks:
        total += m
    return total / len(marks)
'''.splitlines(keepends=True)

after = '''def average(marks):
    if not marks:
        return None
    return sum(marks) / len(marks)
'''.splitlines(keepends=True)

for line in difflib.unified_diff(before, after, 'average_v1.py', 'average_v2.py'):
    print(line, end='')

ratio = difflib.SequenceMatcher(None, before, after).ratio()
print('similarity:', round(ratio, 2))
```

**What the diff prints** (Output)
```output
--- average_v1.py
+++ average_v2.py
@@ -1,5 +1,4 @@
 def average(marks):
-    total = 0
-    for m in marks:
-        total += m
-    return total / len(marks)
+    if not marks:
+        return None
+    return sum(marks) / len(marks)
similarity: 0.22
```
Pasted unchanged from the same Python 3.14 session; Git and most review tools show changes in this unified format.

Is returning None the right fix? That is a design question worth arguing in English. Some teams would rather raise a clear ValueError; others return 0. A good review ends in a decision both people can explain, which is exactly the kind of conversation our mentors hold with learners every week.

1. **Predict.** What does Version 2 return for [], and for [20]?
2. **Argue.** Write two English sentences for and against returning None.
3. **Change it.** Make Version 2 raise ValueError instead, then regenerate the diff.
4. **Review someone.** Swap code with a classmate and leave three comments on their diff.

## How can you check a bootcamp's claims before paying?

By asking for things that can be checked. These questions work for any bootcamp, course or school in Peru, and we expect to be asked them too.

1. **Ask how outcomes are measured.** If a provider quotes a job rate, ask who was counted, over what period, and whether anyone outside the company checked it.
2. **Ask what the certificate is.** Article 46 of the 2014 text of Peru's university law says that even a university's own continuing-education programmes lead to no degree or professional title; they only certify that a learner passed. A private course certificate is not a degree either.
3. **Ask for the syllabus week by week.** Look for testing, Git, databases and a project you design yourself, not only tutorials followed step by step.
4. **Ask about the language.** Which language is every lesson, every piece of feedback and every interview practice in?
5. **Ask what happens if you fall behind.** Repeat a module, move cohort, pause, or lose your place?
6. **Ask for a sample class.** Watch how much time is spent on your code rather than the teacher's.
7. **Read the payment and refund terms.** Especially for any plan that links fees to future income.
8. **Talk to a graduate yourself.** One you find, not one the provider chooses.

### Exams with a defined syllabus

If you want a credential with a clear meaning, consider an exam set by an independent body. The Python Institute describes its PCEP as a 35-question exam lasting 50 minutes, passed at 70%. MINEDU's Fábrica de Programadores pilot trained 1,000 students of 4° and 5° de secundaria in Lima Norte in Python and lets those who finish both stages sit the PCEP.

We prepare learners for the PCEP in our certification course; the Python Institute sets and awards it, not us.

We make no job or salary promise. We teach the skills that employer frameworks list, such as programming, testing, Git and clear communication in English, and help you build projects you can show. Hiring decisions belong to employers.

Not at all. For someone who can study full-time for a few months, a good bootcamp can be a strong choice. Check its claims with the questions on this page before paying, as you should with us.

It varies widely. Our own outline for a beginner with two classes a week runs about a year to a finished, deployed project. Some move faster, some slower; we tell you honestly where you are.
