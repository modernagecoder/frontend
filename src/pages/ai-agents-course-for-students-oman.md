## An agent is not a chatbot with a confident tone

|  | A script | A chatbot | An agent |
|---|---|---|---|
| Given | The steps | The words | The goal |
| Decides | Nothing | What to say | What to do next |
| Can use tools | Only what you coded | No | Yes, and picks which |
| Fails by | Crashing, loudly | Answering wrongly | Doing the wrong thing confidently |
| Hard part | Writing it | Phrasing the request | Knowing what it did and why |

The row that matters is the last one. A script is told the steps. A chatbot is told the words. **An agent is told the goal and works out the steps itself**, which is why it is powerful and why it is dangerous. A program that chooses its own actions can choose wrong ones, with exactly the fluency it uses when it chooses right ones.

So the engineering question is not how to make an agent do something impressive. Any teenager can do that in an afternoon now. The question is how to build one whose mistakes are visible, which is most of the work and almost none of the marketing.

That is why this sits at rung four rather than rung one. A student who cannot handle data has no way to check what their agent did. One who has never measured a model's error has no instinct for the fact that confident output and correct output differ.

## Six steps from a goal to an agent you would let near something real

1. **Write the goal down in one sentence, then argue with it.** "Summarise my emails" is a wish, not a goal: no test of success, no boundary. The student rewrites until a stranger could tell whether it had been achieved.
2. **Give it exactly the tools it needs and nothing else.** Each tool written by hand so the student knows precisely what it can touch.
3. **Make it decompose the goal, then look at the plan before it runs.** This single pause catches most disasters, and it is the professional practice too.
4. **Bound it, three ways.** Maximum steps, fixed tool set, hard stop on loops. Students discover why by building one without bounds and watching it circle for twenty minutes.
5. **Log every decision.** What it decided, which tool it called, what came back, what it concluded. The log is the deliverable as much as the agent.
6. **Break it deliberately and write down what happened.** Contradictory data, a missing file, a tool returning nonsense. The correct behaviour is a clear stop; the common behaviour is to carry on plausibly.

**The three properties we insist on:** bounded, so there is a limit it cannot exceed; legible, so every decision is recoverable afterwards; and loud in failure, so the default when something goes wrong is to stop and say so rather than continue plausibly.

## Four ways an agent goes wrong

- **It loops.** Same step, repeatedly. Symptom: nothing visibly wrong, twenty minutes gone.
- **It hallucinates a tool.** Invents a call rather than reporting a gap. Symptom: an error about a function nobody wrote. The fix is a validation layer, about fifteen lines.
- **It succeeds at the wrong goal.** Does exactly what it was told, which was not what was meant. Symptom: a perfect result that is useless. No technical fix; the fix is step one.
- **It fails quietly.** A tool returns nonsense and the agent produces a fluent summary anyway. Symptom: nothing at all, until somebody checks. This is the expensive one.

Frameworks are replaced roughly annually. Those four failure modes have been the same since people started building these systems.

## What students never do

Every agent built here operates on data the student controls, in an environment that can be reset. It does not send messages on anybody's behalf, spend money, or touch a real account. Learning judgement about consequence requires being free to fail badly, and that is only safe when the blast radius is a sandbox.
