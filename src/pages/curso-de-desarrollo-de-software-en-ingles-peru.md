## ¿Qué se aprende en un curso de desarrollo de software?

Mucho más que un lenguaje. Un desarrollador de software entiende el problema, diseña una solución, la escribe, la prueba, la guarda con historia y la mantiene cuando cambian las reglas. El curso recorre ese ciclo entero.

### Antes del código

Leer un pedido, hacer preguntas, escribir qué debe pasar en cada caso. La mitad de los errores de un sistema nacen en un requisito mal entendido, no en una línea mal escrita.

### Durante el código

Funciones cortas, nombres claros, clases que protegen sus propias reglas, pruebas automáticas que corren con un comando. Es el centro de la lección de ejemplo.

### Después del código

Git para guardar cada cambio con un mensaje que explica por qué, revisión entre pares, documentación mínima y la costumbre de dejar el proyecto un poco más ordenado de como se encontró.

## ¿Qué significa diseñar software y no solo programar?

Significa decidir quién es responsable de cada regla. Esta lección, escrita por nosotros, usa un caso que conocemos bien: un grupo de clase con cupo limitado y sin alumnos repetidos.

**Versión 1: un diccionario sin reglas** (Python)
```python
python_b = {'name': 'Python B', 'capacity': 3, 'students': []}
for s in ['Ana', 'Luis', 'Ana', 'Rosa', 'Jorge']:
    python_b['students'].append(s)
print(python_b['students'], len(python_b['students']), 'of', python_b['capacity'])
```
Pregunta del mentor antes de ejecutar: "How many students can this group hold, and how many will it end up with?"

**Salida de la versión 1** (Salida)
```salida
['Ana', 'Luis', 'Ana', 'Rosa', 'Jorge'] 5 of 3
```
Copiado tal cual de nuestra ejecución con Python 3: cinco inscritos en un grupo de tres, y Ana dos veces.

La versión 1 no tiene errores de sintaxis y corre sin quejarse. El problema es de diseño: el cupo existe como dato, pero nadie lo hace cumplir. Cualquier parte del programa puede añadir un nombre a la lista, y basta con que una sola se olvide de revisar el cupo para que el grupo quede con cinco personas. En un sistema real, ese olvido se paga con dos alumnos que se presentan a una clase que no tiene sitio para ellos.

**Versión 2: la clase protege sus propias reglas** (Python)
```python
class Group:
    def __init__(self, name, capacity):
        self.name = name
        self.capacity = capacity
        self.students = []

    def enrol(self, student):
        if student in self.students:
            raise ValueError(f'{student} is already in {self.name}')
        if len(self.students) >= self.capacity:
            raise ValueError(f'{self.name} is full ({self.capacity})')
        self.students.append(student)


python = Group('Python B', capacity=3)
for s in ['Ana', 'Luis', 'Ana', 'Rosa', 'Jorge']:
    try:
        python.enrol(s)
        print('enrolled', s)
    except ValueError as e:
        print('refused:', e)
print(python.students)
```
La única forma de inscribir es el método enrol, y el método se niega con raise ValueError cuando una regla no se cumple.

**Salida de la versión 2** (Salida)
```salida
enrolled Ana
enrolled Luis
refused: Ana is already in Python B
enrolled Rosa
refused: Python B is full (3)
['Ana', 'Luis', 'Rosa']
```
Resultado exacto de correr el archivo nosotros mismos. La lista final tiene tres personas y ninguna repetida.

1. **La regla vive en un solo lugar.** El cupo y la prohibición de repetidos están dentro de Group. Si mañana cambia el cupo, se cambia ahí y en ningún otro sitio. En inglés esto se llama mantener un invariant.
2. **La clase no decide qué hacer con el rechazo.** Solo avisa con una excepción. Quien llama, con try y except, decide si muestra un mensaje, ofrece otro grupo o anota a la persona en una lista de espera.
3. **El mensaje dice qué pasó.** "Ana is already in Python B" es más útil que "Error". Un buen mensaje ahorra horas a quien mantiene el sistema dentro de un año.
4. **El reto.** Añadir un método drop(student) que saque a alguien del grupo y que lance un error si esa persona no estaba inscrita. Luego predecir qué imprime el programa si Rosa se retira antes de que llegue Jorge.

Elegimos un grupo de clase a propósito: nuestras clases grupales son de quince a veinte personas, y el sistema que las organiza tiene exactamente estas reglas. Es un recordatorio de que el software que usamos todos los días está lleno de pequeños invariantes que alguien tuvo que proteger. Aprender a verlos, nombrarlos y defenderlos en el código es la diferencia entre escribir programas y desarrollar software.

## ¿Qué es el desarrollo seguro de software?

Es escribir el código pensando desde el inicio en lo que puede salir mal a propósito, no solo por accidente. El estudio de PROMPERÚ lo resume en una frase: la seguridad deja de ser un módulo adicional y pasa a integrarse desde el diseño del software.

### Hábitos que enseñamos desde el principio

No confiar en lo que llega de afuera: todo dato que escribe un usuario o que envía otro sistema se valida antes de usarse, como hace el método enrol con los nombres repetidos.

No guardar contraseñas ni claves dentro del código, y no subirlas nunca a un repositorio público. Se usan variables de entorno y archivos que Git ignora.

### Hábitos que llegan después

Consultas a bases de datos con parámetros, nunca armando el texto de la consulta a mano, para evitar inyecciones de SQL.

Dar a cada parte del sistema el mínimo de permisos que necesita, y registrar lo que pasa para poder investigar un incidente.

Quien quiere profundizar en seguridad tiene en el catálogo un curso de hacking ético, siempre con fines defensivos y sobre sistemas propios o autorizados. Para el resto, la seguridad no es un curso aparte: es una pregunta que el mentor hace en cada revisión de código. ¿Qué pasa si alguien escribe esto a propósito?

### Para quien empieza

El salto del nivel 2 al 3 cuesta: pensar en objetos y responsabilidades es una forma nueva de ver los programas. Es normal que tome varias semanas.
Una buena señal es que empiece a preguntarse "¿a quién le toca revisar esto?" antes de escribir.

### Para quien ya programa

Muchas personas autodidactas llegan con nivel 2 y saltan al 4 sin pasar por el 3. El curso les pide volver al diseño.
Las pruebas automáticas suelen ser la parte más nueva y la que más cambia la manera de trabajar.
