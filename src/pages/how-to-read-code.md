# You read far more code than you write. Nobody taught you how.

> Reading code is a procedure rather than a talent, and it is the skill programmers use most and are taught least. The method is four passes in a fixed order: what goes in and out, follow one item through, what happens to the leftovers, then name the thing yourself. It scales from a single function to a large repository. Modern Age Coders teaches it live because reading is the one programming skill with no feedback loop: form a wrong understanding and nothing happens at all, so a teacher has to supply the correction. ## The asymmetry

Every course is production-shaped: here is a blank file, produce a solution. Almost none is comprehension-shaped: here are four hundred lines you did not write, tell me what happens when the input is empty.

The second exercise is closer to the job. Nobody joining a team is asked to write for the first weeks; they are asked to understand. And agents made the gap extreme, because a student can now generate more code in an afternoon than they can carefully read in a week. If you read two hundred lines an hour and your tools emit two thousand, your reading speed is your engineering speed.

## The four passes

Applied to a single unfamiliar function, or to a repository of two hundred thousand lines. Only the unit changes.

1. **What goes in, what comes out?** Two collections in, one array out, so it is a merge. Nothing else matters yet.
2. **Follow one item through.** Ignore every branch it does not take. This single technique does more than any other.
3. **What happens to the leftovers?** The items that were in the old set and not the new one. Often the actual purpose of the code.
4. **Name it yourself, in one sentence.** If you cannot write the sentence, you have not finished reading, whatever the feeling of understanding says.

## Walking into an unfamiliar codebase

- **Find what runs first**, not the first file alphabetically. The route handler, the main function, the listener.
- **Read the shapes before the logic.** Most functions are obvious once you know exactly what they are handed.
- **Give yourself twenty minutes** before asking anybody. Long enough to build a real question, short enough not to lose a day to pride.
- **Read the tests first.** They are documentation that cannot go out of date, because they fail when they lie.
- **Use the history.** A confusing line is often the residue of a specific bug, and the commit that introduced it frequently says why.
- **Change something small and predict what breaks.** The only feedback reading naturally provides.

## Beginner and reader, side by side

| Situation | A beginner | A reader |
|---|---|---|
| New repository | Starts at the first file | Finds what runs first |
| Unknown function | Reads every line | Checks inputs and outputs, stops |
| Unfamiliar name | Stops to look it up | Assumes, continues, verifies later |
| Long file | Scrolls, feels defeated | Traces one item, ignores the rest |
| Finishing | Feels they understand | Writes one sentence saying what it is for |

## Why it needs a teacher

Reading is the one programming skill with no feedback loop. Write wrong code and it breaks. Read code wrongly and nothing happens at all: you walk away confident and incorrect, and find out three weeks later or never. Somebody who knows the code has to ask the question that exposes the gap. The material is real code only, never textbook code, which is written to be understood and therefore teaches nothing about reading code written to be finished.
