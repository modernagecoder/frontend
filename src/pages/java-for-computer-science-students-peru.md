## What should every computer science graduate know?

A widely cited international answer is CS2023, the computer science curriculum report of the ACM, the IEEE Computer Society and AAAI. It names a "CS Core" that every graduate should cover and estimates it at 270 hours of class time, spread across seventeen knowledge areas.

**CS2023 core hours by knowledge area (selected areas, with the total)**

| Knowledge area | CS Core hours | KA Core hours |
|---|---|---|
| Software Development Fundamentals (SDF) | 43 | none listed |
| Algorithmic Foundations (AL) | 32 | 32 |
| Foundations of Programming Languages (FPL) | 21 | 19 |
| Mathematical and Statistical Foundations (MSF) | 55 | 145 |
| Society, Ethics, and the Profession (SEP) | 18 | 14 |
| Systems Fundamentals (SF) | 18 | 8 |
| Artificial Intelligence (AI) | 12 | 18 |
| Data Management (DM) | 10 | 26 |
| Software Engineering (SE) | 6 | 21 |
| All seventeen areas | 270 | not totalled |

Source: ACM/IEEE-CS/AAAI, Computer Science Curricula 2023 (CS2023), "Introduction to the Knowledge Model", Table 2, read on 9 November 2026 and checked against the rendered PDF page. The report was endorsed by ACM on 18 January 2024, IEEE-CS on 22 January 2024 and AAAI on 22 February 2024, and a Spanish version is available on the CS2023 site. Eight smaller areas are left out of this table; their hours are included in the 270.

### How to read it

CS Core topics are the ones every graduate should meet. KA Core topics are the deeper material a programme may choose to cover in some areas and not others. CS2023 assumes a typical course meets for about 40 instructional hours, so by our arithmetic the CS Core alone is close to seven full courses.

Three areas carry most of the programming: Software Development Fundamentals, Algorithmic Foundations and Foundations of Programming Languages. Together they make up 96 of the 270 CS Core hours, about 36% by our calculation.

### Where Java comes in

CS2023 does not prescribe a language. Java is simply one of the common vehicles for those three areas: it has classes and interfaces for design, a large collections library for data structures, and a strict type system that makes many errors visible early.

So a student who learns Java well is not learning "a Java course". They are covering a large share of what the international curriculum treats as non-negotiable, and the ideas transfer to C++, Python, Kotlin or C# afterwards.

## Is competitive programming worth it for a CS student in Peru?

For many students, yes, because it turns algorithms from a chapter into a reflex. Peruvian universities take it seriously: the Universidad de Lima's algorithm circle lists among its aims preparing teams for the ICPC and IEEExtreme contests, and running internal contests in the ICPC format.

### What contests test

Reading a precise problem in English, choosing an algorithm whose running time fits the limits, writing it correctly under time pressure, and testing the edge cases before the judge does.

### Where Java fits

Java's collections, comparators and big-number support make it a capable contest language. C++ is faster to run and more common at the top; many students compete in both, and we teach both.

### How rankings work

Contest scoreboards rank by problems solved and break ties by time. Peru's school olympiad, the OPI, states the same idea in its 2025 rules: score first, then time penalty, used only to separate ties.

That last point is the starting idea for our lesson. A ranking is just a sort, and a sort is only as good as its rule for ties. Contest organisers write tie rules down for exactly that reason, and a programmer who forgets them produces a scoreboard that looks right and is not. We are not connected with the ICPC, IEEE or UTEC's OPI; the problems we use in class are our own.

## How do you sort a contest scoreboard correctly in Java?

With a comparator that breaks every tie. This lesson, which we teach to university students in their first data structures months, uses an invented five-person scoreboard and Java 21's records and comparators.

### The setup

Five contestants, each with problems solved and penalty minutes. The rule: more problems solved ranks higher; on a tie, fewer minutes ranks higher; if that ties too, order by name so the result never depends on luck.

Most students write the first sort quickly: problems solved, highest first. It compiles, runs and looks plausible.

### The trap

Look at the first output. Diego and Bruno both solved 5 in 260 minutes, and Diego comes first only because he was entered first. Valeria, with 210 minutes, ranks above Ana with 180, which breaks the rule.

Java did nothing wrong. Its documentation says Collections.sort is **guaranteed to be stable**: equal elements are not reordered. Elements the comparator calls equal simply stay in their input order, so the comparator must say everything the rule says.

**Ranking.java: one comparator that misses ties, one that settles them** (Java)
```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

public class Ranking {
    record Entry(String name, int solved, int minutes) {}

    public static void main(String[] args) {
        List<Entry> board = new ArrayList<>(List.of(
            new Entry("Valeria", 4, 210),
            new Entry("Diego", 5, 260),
            new Entry("Ana", 4, 180),
            new Entry("Bruno", 5, 260),
            new Entry("Camila", 3, 95)
        ));

        board.sort(Comparator.comparingInt(Entry::solved).reversed());
        System.out.println("By solved only:");
        board.forEach(e -> System.out.println("  " + e));

        board.sort(Comparator.comparingInt(Entry::solved).reversed()
                .thenComparingInt(Entry::minutes)
                .thenComparing(Entry::name));
        System.out.println("Solved, then minutes, then name:");
        board.forEach(e -> System.out.println("  " + e));
    }
}
```
Compiled and run with JDK 21, the first block prints Diego, Bruno, Valeria, Ana, Camila (for example Entry[name=Diego, solved=5, minutes=260] first). The second prints Entry[name=Bruno, solved=5, minutes=260], then Diego, Ana, Valeria and Camila.

The fix is a chain: thenComparingInt(Entry::minutes) settles ties on solved problems, and thenComparing(Entry::name) settles the rare full tie. Now Ana correctly passes Valeria, and Bruno and Diego appear in alphabetical order whatever order they were entered in. **A stable sort keeps your input order for ties; only your comparator can replace it with a rule.**

The Comparator documentation adds the contract behind all of this: comparing x with y must give the opposite sign to comparing y with x, and the relation must be transitive. Comparators that break the contract can make sorting behave unpredictably, which is why we teach students to build them from comparingInt and thenComparing rather than hand-written subtraction. The scoreboard and names are ours, invented for the exercise.

1. **Predict.** Swap Diego and Bruno in the input list and run the first sort again. What changes, and why does the second sort not change at all?
2. **Reverse one key.** Change the rule so that more minutes ranks higher. Which single call do you edit, and what happens if you put reversed() at the very end of the chain instead?
3. **Prove stability.** Sort first by name, then by solved problems only. Explain, in English, why the names inside each group are now alphabetical.
4. **Scale it.** Generate 100,000 random entries and time both sorts. Then read the complexity of List.sort in the documentation and say whether your timings agree.

## Should a CS student use AI to write Java assignments?

Your university decides what is allowed in its coursework, and you should follow its rules. Our view is simpler: if you cannot explain why a comparator is correct, you have not finished the exercise, whoever wrote the code.

### Rules before tools

Write the rule in a sentence first, as in the scoreboard lesson: solved, then minutes, then name. The code is a translation of that sentence, and most bugs are a sentence that was never written.

### Read the documentation

The stable-sort guarantee and the comparator contract are both in the official Java documentation, in English. A student who reads it can answer questions that a pasted answer never raises.

### AI as a critic

Claude is for users aged 18 and over. University students may use such tools to criticise their own designs, within the rules of their course, never to hand in code they cannot defend line by line.

Whether you study in Lima, Arequipa, Trujillo or Cusco, the teaching standard is the same: reasoning first, code second, and an honest answer when a topic is harder than your course made it look.
